# 01. Архитектура и обоснование

## 1. Выбор способа интеграции

| Критерий | A. HTTPS API сайта `/api/extension/v1` | B. Мост страницы (`postMessage` + content script) | **C. Гибрид (выбран): B + импорт файла** |
|---|---|---|---|
| Что нужно на сайте | новый серверный компонент (Node/…): хранение, авторизация, идемпотентность, защита | модуль в бандле сайта (≈500 строк), без сервера | то же, что B |
| Секреты и токены | нужны (токен расширения), риск утечки, срок жизни, ротация | **нет** — данные не покидают браузер | нет |
| Логика генерации | пришлось бы переносить/дублировать или запускать движок на сервере | остаётся в бандле сайта — **единственный источник** | остаётся на сайте |
| Поверхность атаки | новый публичный эндпоинт | `event.source/origin`, белый список типов, строгая схема | то же |
| Работа без развёрнутого моста | — | нет | **да**: импорт JSON/JSONL/TXT-экспорта сайта без изменений сайта |
| Соответствие факту «сайт офлайн» | противоречит | соответствует | соответствует |

**Решение:** сайт остаётся источником генерации (движок в его бандле), расширение — локальный исполнитель очереди. Канал — версионированный мост протокола v1 (`docs/02-CONTRACT.md`);
запасной путь — импорт файла (режим C). Контракт `rps-batch/1` не зависит от транспорта: при появлении серверного `/api/extension/v1` его можно отдавать тем же объектом.

## 2. Компоненты

```text
 вкладка сайта                 service worker (владелец состояния)                  вкладка ChatGPT
┌───────────────┐  postMessage ┌────────────────────────────────────────────┐  sendMessage ┌─────────────────┐
│ движок+рендер │◄────────────►│ Orchestrator (FSM, очередь, повторы)        │◄────────────►│ content/chatgpt │
│ extension-    │ site-bridge  │ Store → chrome.storage.local (атомарно)      │  команды:    │ снимок DOM,     │
│ bridge (TS)   │ (relay)      │ Adapters: вкладка, fetch, downloads, сайт   │  SUBMIT/WAIT │ вставка, «Стоп» │
└───────────────┘              │ alarms-watchdog, уведомления, значок       │  LOCATE/…    └─────────────────┘
                               └──────────────▲─────────────────────────────┘
                                    port rps-panel / sendMessage
                               ┌──────────────┴─────────────┐
                               │ панель (side panel, RU)     │   файлы: chrome.downloads →
                               └─────────────────────────────┘   <Загрузки>/<папка>/Batch_…/Character_…/NNN.png
```

* **service worker** — единственный владелец состояния; UI и content scripts без состояния очереди. Слушатели регистрируются на верхнем уровне.
* **Orchestrator** не зависит от `chrome.*` (внедряемые адаптеры) — поэтому полностью тестируется без браузера.
* **content/chatgpt.js** отвечает на команды и **сам ничего не делает**; решение «готово/ошибка/блокировка» принимают чистые функции `analyzeSnapshot/decideWait` (одни и те же в content script и в тестах).
* **Панель** — «окно» к состоянию: закрытие панели очередь не останавливает (проверено e2e).

## 3. Конечный автомат и надёжность

Состояния: `idle, preparing, submitting, waiting, downloading, verifying, completed, retryable_error, paused, blocked, failed`.
Допустимые переходы заданы таблицей (`lib/fsm.js`, `docs/02-CONTRACT.md §4`); любой другой переход отвергается (`IllegalTransition`).
Каждый переход — **одна запись** в `chrome.storage.local` (раннер + задание + событие журнала).

Следующий промпт уходит только после `verifying → completed`: изображение найдено **по наблюдению интерфейса** (кнопка «Стоп» исчезла, новое изображение полностью загружено и стабильно 2,5 с, не из базовой линии и не уже использованное), исходный файл получен и проверен (формат по байтам, размер ≥ порога, SHA-256, не дубликат), `chrome.downloads` сообщил `complete`, `exists`, размер файла совпал, затем пауза интервала.

**Восстановление**
* Выгрузка service worker: состояние читается из хранилища; шаг `waiting` продолжается нарезками по 20 с (долгие вызовы удерживают worker живым), watchdog-будильник (30 с) будит выгруженный worker.
* Повторной отправки нет: у каждой фактической отправки уникальный `submit_seq` → токен; content script по тому же токену возвращает прежнее подтверждение; перед повтором выполняется `locate` — поиск уже отправленного промпта в беседе (по нормализованному префиксу).
* Перезапуск Chrome/расширения: очередь ставится на **паузу** (`BROWSER_RESTART`/`EXTENSION_UPDATE`) — автоматизация без действия пользователя не возобновляется.
* Закрыта вкладка → `blocked: TAB_CLOSED`; после открытия ChatGPT «Продолжить» возвращает вкладку в сохранённую беседу и ищет отправленный промпт.
* Ошибки скачивания: повтор берёт уже найденные изображения (**без новой генерации**), отдельный счётчик попыток; `RETRY_FAILED` делает то же.
* Дубликаты: идемпотентный `batch_id`; уникальные `image_job_id`; ключи уже использованных изображений (не берутся повторно); SHA-256 против дублей внутри партии; `conflictAction: overwrite` для того же задания (никаких «(1)»).

**Блокировки без обхода:** CAPTCHA/Cloudflare, потеря входа, лимит, изменение интерфейса, закрытая вкладка, чужая генерация на странице → `blocked` + уведомление + значок «!».
Повторяются только временные ошибки с нарастающей задержкой (15 с → 5 мин), сетевые — без расхода попыток (до 15 мин, затем `OFFLINE`).
Зависшую собственную генерацию расширение останавливает кнопкой «Стоп» перед повтором.

## 4. Идентичность персонажей: стратегия

| Приём | Статус |
|---|---|
| Неизменное ядро внешности отдельно от стайлинга кадра, отпечаток SHA-256, проверка при приёме партии и при сборке на сайте | реализован |
| Текст внешности повторяется в каждом промпте (рендерер сайта) | реализован |
| **Отдельная беседа на каждого персонажа** (изоляция контекста; нет смешивания) | реализован, по умолчанию |
| Кадры одного персонажа — в одной беседе (модель видит прежние изображения), ротация беседы каждые 12 кадров (длинные беседы деградируют) | реализован, настраивается |
| Различие персонажей партии минимум по 4 полям ядра | реализован на сайте |
| Ручная проверка результата (кнопка показа файла, папки по персонажам) | реализован |
| Референс-изображение | **исследовано, не реализовано** (см. ниже) |

*Новая беседа, продолжение беседы, референс.* Новая беседа изолирует контекст, но модель не «помнит» лицо из прошлых кадров. Продолжение беседы даёт модели прежние изображения и обычно повышает сходство,
но длинный контекст замедляет и «дрейфует»; поэтому выбрана связка «один персонаж = одна беседа + ротация». Прикрепление референса технически возможно (поле выбора файла в поле ввода), но не реализовано:
без живого аккаунта поведение не проверить, результат зависит от моделей и продуктовых ограничений ChatGPT, а зависимость «следующий кадр — от файла предыдущего» усложняет восстановление. Контракт резервирует `reference: null`.
**Идентичность лица не гарантируется.**

## 5. Файлы и метаданные

`<Загрузки>/<rootFolder>/Batch_ГГГГ-ММ-ДД_NNN/{manifest.json, Character_001/{character.json, prompts.jsonl, 001.png, …}}`.
Расширение — по реальному формату (png/jpg/webp/gif), перекодирования нет. Номер партии за день хранится в хранилище (имена не повторяются).
`chrome.downloads` пишет только внутрь папки загрузок Chrome (другой диск — в `chrome://settings/downloads`); произвольный доступ к файловой системе не запрашивается.
ZIP изображений не делается (хранить гигабайты в расширении нельзя): альтернатива — заархивировать папку партии; метаданные и журнал экспортируются из панели.

## 6. Безопасность

| Разрешение | Зачем |
|---|---|
| `storage`, `unlimitedStorage` | состояние очереди (партии до 1500 заданий и журнал) |
| `downloads` | сохранение файлов и метаданных |
| `alarms` | watchdog для выгружаемого service worker (только пока очередь активна) |
| `sidePanel` | панель управления |
| `scripting` | внедрение content script в уже открытые вкладки |
| `notifications` | уведомление об остановке/завершении |
| host `chatgpt.com`, `*.oaiusercontent.com`, `promts.vibecods.xyz` | наблюдение за вкладкой, получение исходного файла, мост сайта |

Нет: `tabs`, `activeTab`, `cookies`, `identity`, широких host-доступов, `web_accessible_resources`, `externally_connectable`, удалённого кода, `eval`, `innerHTML` с пользовательским текстом (проверяется сборкой).
Сообщения проверяются строго (`sender.id`, URL отправителя, белый список типов, типы и размеры полей); адреса изображений — только `https` и хосты ChatGPT/OpenAI; ссылка беседы — только `https://chatgpt.com/`.
Пароли и cookie не читаются и не сохраняются; в журнал не пишутся токены, подписи URL и содержимое страниц сверх коротких сообщений об ошибках.
